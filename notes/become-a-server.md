# 把一台普通电脑变成"服务器"——资料包

> 给 netforce 智能体的参考资料。搜于 2026-10-17，2026-10-17 二次校正目的。

## 🔴 零、先校正目的：我们要的不是"对外建站"，是"让 AI 能用这台电脑"

如果目标是**让 AI 更好地使用这台电脑**（调用它的算力、文件、脚本、网络），
那么"变成服务器"这件事的性质完全变了——**不是让陌生人能访问我，而是让被授权的一方随时能叫我干活。**

这个区别决定了全部选型：

| | 对外建站（传统理解） | **给 AI 用（我们的真实目的）** |
|---|---|---|
| 谁来访问 | 任意陌生人 | 只有被授权的 AI / 你自己 |
| 是否需要公网 IP | 需要（否则没人找得到） | **不需要** |
| 是否需要开放入站端口 | 需要（80/443…） | **完全不需要** |
| 攻击面 | 暴露在公网，要防扫描/爆破 | **零入站 ⇒ 攻击面为零** |
| 合规负担 | ICP 备案、家宽条款限制 | 不涉及对外信息服务 |
| 关键能力 | 带宽、可用性 | **能力接口 + 授权 + 审计** |

**所以正确形态是"出网借道"，不是"开放端口"**：
本机主动出网连上一个会合点并保持长连（心跳），指令沿着这条**已经建立的出网连接反向送回来**。
零公网 IP、零端口映射、路由器不用配、防火墙不用开——因为压根没有入站连接。

### 🔴 定调：别把这件事理解成"建站"

**建站对我们没有实际效益**——我们不需要一个被陌生人访问的网站。
要做的事只有一件：**让 AI 更好地与我们交互**（它能随时叫得动这台电脑、能读能写能跑，我们就多了一个真正干活的帮手）。

由此推论：
- **不要去折腾公网、备案、经营性建站这些**——它们跟我们要解决的问题无关，纯属岔路。
  （真要做对外建站，直接买台国外 VPS 更省事，那不是一个问题域，本资料不展开。）
- **不要自己跟路由器/端口转发死磕**：CGNAT 下开端口映射本来就没用（WAN 口是私网地址），
  需要转发就**用现成的代理/转发节点**（见第二节后的补充），把这一段交给它们。
- 我们真正要造的是**交互能力**，不是**可达性**。可达性只是手段，而且是可以外包给现成基础设施的手段。

**这条路上"服务器"三个字其实是误导**：我们不需要它像服务器一样被访问，
只需要它像一个**随时在线、能被叫得动、叫得动之后能真干活的节点**。

> 这正好就是 netforce 在做的东西：`agent_cli`（给个文件夹就能干活）+ `heartbeat_relay`（出网长连/心跳/反推）+ `tool_agent`（EXEC/READ/WRITE 真工具）＝ 这套形态的原型。
> 下面第二、三节的传统方案矩阵仍然有用，但**只作为对照与兜底参考**，不是我们要照抄的目标。

## 一、（原结论）先判处境：三件事决定你能用哪条路

> 结论先行（校正前版本，保留作对照）：**"变成服务器"要解决的是"别人怎么主动找到你"，不是性能问题。**
> 唯一的硬障碍是 NAT / CGNAT（你没有被分配的公网地址，入站连接无处可寻）。
> 所有方案的本质只有两类：**你有可路由地址**（直连），或**你主动出网去某个中转点借地址**（反向）。

---

## 一、先判处境：三件事决定你能用哪条路

动手前先测这三样，不测就选方案等于瞎试：

| 要测的 | 怎么测 | 结果含义 |
|---|---|---|
| 有没有公网 IPv4 | 路由器 WAN 口 IP 与 `ip.cn` / 百度"IP"看到的公网 IP 比对；一致则有 | 一致 = 可端口映射；不一致 = CGNAT 大内网 |
| 有没有 IPv6 | 访问 test-ipv6.com；本机 `ipconfig` 看有没有非 `fe80::` 地址 | 有 IPv6 = 可原生直连（但访问方也得有 IPv6） |
| 80/443 是否可用 | 家宽普遍封 80/443 | 被封就走非标端口或隧道 |

**CGNAT 是绝大多数人的现实**：IPFS Amino DHT 实测约 **91% 的 peer 位于 NAT 之后**（ProbeLab 测量）。所以下面的方案里，"出网借道"是主流，不是偏门。

## 二、方案矩阵（工程上真正可选的六条路）

| 方案 | 原理 | 要公网 IP？ | 要中转机？ | 能给外人访问？ | 适用 |
|---|---|---|---|---|---|
| 端口映射 + DDNS | 路由器把外网端口转到内网 | **要** | 否 | 能 | 能要到公网 IPv4，延迟最低 |
| IPv6 + DDNS | 本机直接持有全球唯一地址 | 不要（要 IPv6） | 否 | 能（访问方须有 IPv6） | 家宽已通 IPv6，首选试 |
| frp / rathole / chisel / bore / sish + VPS | 本机主动连 VPS，反向代理 | 不要 | **要**（几十元/年） | 能 | 要完全自控、流量大 |
| Cloudflare Tunnel / 腾讯 EdgeOne 隧道 | 本机跑守护进程连边缘节点 | 不要 | 不要（第三方） | 能 | 零成本、自带 HTTPS，最省事 |
| Tailscale / Headscale / Netbird / ZeroTier | 虚拟组网（Overlay） | 不要 | 不要 | **不能**（只给自家设备） | 自己远程回家，最安全 |
| 花生壳 / natapp / cpolar / ngrok | 商业 SaaS 穿透 | 不要 | 不要 | 能 | 零门槛，接受限速与数据过第三方 |

补充自托管选项（自建控平面，不依赖厂商）：**Pangolin + Newt**（自建 CF Tunnel 等价物，带面板）、**Headscale**（自建 Tailscale 控制面）、**zrok**（开源 ngrok）、**ssh -R 反向隧道**（最原始但零依赖）。

**决策树（直接对号入座）**

- 能打电话要到公网 IPv4 → 端口映射 + DDNS（80/443 被封就用非标端口）
- CGNAT、愿意花几十元/年 → frp + 轻量 VPS，带宽自控
- CGNAT、想零成本省事 → Cloudflare Tunnel（海外）/ EdgeOne（国内）
- 只有自己的设备要远程回家 → Tailscale / ZeroTier
- 要完全自控、不接受数据过第三方 → 自建 frp / Pangolin / Headscale

## 二·补、需要转发时，用现成的代理/转发节点，别自己折腾

真遇到"某个端口需要被访问到"的场景，**不要去路由器开端口映射**（CGNAT 下 WAN 口是私网地址，开了也没用），
直接**借现成的转发能力**：

- **自有 VPS 反向隧道**：`ssh -R` / sish / frp / rathole，把本地端口挂到有地址的一端。
- **代理节点转发**：用现成的代理/中继节点做转发，本机只管出网，地址问题甩给节点。
- **商业穿透**：natapp / cpolar / ngrok，零配置，代价是数据过第三方、有限速。

**这一段和"多重跳转"是同一件事的现实版本**：一跳不通就换一跳，自己没地址就借别人的转发能力，
路不通就绕——网络的本质就是多重跳转。所以转发节点不只是"省事的选择"，它本来就是我们协议里的**一跳**。

**结论**：可达性是可以外包的；不要在这上面投入。精力全部放在**交互能力**（能力接口 + 长连 + 授权 + 审计）上。

## 三、协议层的硬事实（这一段最重要，是唯一带大规模实测数据的）

"打洞"（hole punching）是唯一能绕开中转机的办法，但它**不是 100% 可靠**。2026 年有两份可信测量：

**1) ACM IMC '26 论文（Trautwein 等，哥廷根大学）**
`arXiv:2604.12484`，DOI `10.1145/3777912.3809138`
样本：**440 万次**打洞尝试、8.5 万+ 不同网络、167 个国家（IPFS 生产网，DCUtR 协议）

- 打洞阶段**条件成功率 70% ± 7.1%**（前提是中继预留与公网地址发现已成功）
- **推翻了"UDP 打洞优于 TCP"的长期信念**：TCP 与 QUIC 成功率统计上无差异（均约 70%），因为 DCUtR 用高精度 RTT 同步
- **97.6%** 的成功连接是**第一次尝试**就建立
- 成功与否与中继节点特征无关（说明机制对无许可环境友好）

**2) ProbeLab 复测（按 NAT 类型拆解）**

- Port-Restricted Cone NAT：**82.9%** 打洞成功
- Symmetric NAT：约 **40%**（传统认为不可打洞，实际部分可；但样本仅 536 个 vs cone 3669 个）
- **约 36% 声称支持 DCUtR 的 NAT 节点根本拿不到中继预留** ⇒ 没有中继就没有打洞的入场券
- 可控环境下 go-libp2p 与 rust-libp2p **100% 互通**

**这组数字对我们意味着什么**：即便用最成熟的工业级方案，仍有约 30% 的节点无法直连，必须走中继。而且中继不是可选项而是**前置依赖**——没预留就压根没得打。所以"无中转机"只是理想，**中转/多跳是兜底，不是退化**。

## 三·补、给 AI 用的落地形态（这才是我们该照着做的）

目标：让一个不在本机的 AI，**随时能叫这台电脑干活**，且本机不暴露任何入站端口。

五个必要组件，缺一个都不成立：

1. **能力接口（工具白名单）**：不是把整台电脑交出去，而是只开放一组明确动作——
   `EXEC`（跑代码/命令）、`READ`、`WRITE`、`LIST`，路径**锁死在一个工作区目录内**（`agent_cli.py` 就是这个设计：给一个文件夹，在文件夹里干活）。
   命令黑名单（删盘/格式化/`curl|bash`）在工具层直接拒执行。

   🔴 **不开放删除能力**（用户定调）：工具层没有 DELETE，`EXEC` 里的 `rm` / `del` / `os.remove` / `shutil.rmtree` 等删除类动作**整类封死**。
   理由：删除不可逆，而"自动规则删"迟早会误删真东西——这条在我们自己的资源库上已经验证过（所以那边也是只打标签、零删除）。
   **AI 只增不改不删**：要清理什么，由它在结论里点名，人来执行。
2. **出网长连 + 心跳**：本机主动出网连会合点，周期性心跳保活；指令沿这条连接反向送回。
   断线自动重连——这是"随时在线"的唯一来源，不靠入站。
3. **授权**：谁能叫得动它。令牌/密钥只在出网连接里带，不监听端口就不存在被扫描到的可能。
4. **审计**：每一次调用、每一次 EXEC 的真实输入输出都落盘留痕（我们已有 `work/_traces/`）。
   AI 干过什么必须可回溯，否则不可能放心给它更大的权限。
5. **超时闸**：单个任务卡死要有硬闸（我们的规矩：单 agent 卡 30 分钟才掐，且掐交给同伴监督）。
   没有闸的话，一个死循环就能把机器拖住。

**明确不要做的事**：不要为了"让 AI 能用"去开端口映射、不要开 DMZ、不要暴露 22/3389。
传统建站那套防扫描、防爆破、加 HTTPS 的负担，在"零入站"形态下**根本不存在**——这是这条路线最大的收益，别把它丢掉。

**和现成标准的关系**：业界把"本机能力暴露给远端模型"这件事正在标准化（远程工具调用 / MCP 一类），
思路一致：本地能力以结构化工具描述对外提供，经一条已建立的通道被调用。
我们的特殊约束更严——节点是免费 LLM API（无状态、不能监听端口），
所以连"跑个守护进程"都做不到，只能靠**轮询式心跳**模拟长连，agent 壳与 brain 分离。这是我们的难点，也是创新点。

## 四、和我们正在做的 netforce 协议是什么关系

我们 p003 讨论的协议（出网长连接 + 心跳保活 + 反向推送）在分类上属于**第二类：出网借道**。上表能直接给它定位：

- **Cloudflare Tunnel / frp / DCUtR 的底层思路和我们完全一致**：本机主动出网、连上一个有地址的中间点、把入站流量反向送回来。区别只在于中间点是谁（厂商 / 自有 VPS / 别的 peer）。
- **上面的 70% 是该路线的技术天花板参考**：我们不必重新发明，但要清楚——想让"任意一台能出网的电脑都能被主动推送"，**中继链（多重跳转）是必须的兜底层**，不是可以省略的部分。这正是 p003 第六节"网络的本质是多重跳转"要落地的东西。
- **我们的额外约束比通用方案更严**：节点是免费 LLM API（无状态、不能监听端口），所以连"跑个守护进程"都做不到 ⇒ 只能靠**轮询式心跳**模拟长连，agent 壳与 brain 分离。这是我们的特殊性，也是难点。

## 五、顺带一句（不是重点，别在这上面花时间）

- 我们**不做对外建站**，所以备案、家宽条款这些根本不构成约束。真要做对外建站，直接国外 VPS，那是另一个问题域。
- 唯一值得记的安全常识：别把 22（SSH）/ 3389（远程桌面）/ 3306（MySQL）/ 6379（Redis）暴露出去。
  我们走零入站，天然不涉及——这正是不要去开端口映射的又一个理由。

## 六、给智能体的可动手清单（用 EXEC 真跑，别只说）

目的不是"让外人访问"，而是**让一个不在本机的 AI 能随时叫这台电脑干活**。按难度递增，每步都要真跑：

1. **自检**：本机出口 IP 与路由器 WAN IP 对比 → 判 CGNAT；查有没有全球 IPv6；确认 80/443 不可用。
2. **证明入站不通**：从另一台机器/外网访问本机公网 IP:端口，记录失败——**这就是我们必须走出网路线的动机**，把真实输出贴出来。
3. **出网长连 + 心跳**：本机客户端**主动出网**连会合点并保持心跳；杀掉连接后测多久自动重连成功（自愈耗时）。
4. **反向送指令**：会合点把一个"任务"沿这条已建立的连接推回本机，本机执行并把**真实输出**回传。
   **用纯 Python socket 实现，不依赖任何成品**（frp/ngrok 都不许用），端到端跑通。
5. **工具白名单 + 路径锁**：只开放 `EXEC/READ/WRITE/LIST`，路径锁在工作区内；
   **必须真的跑一次越权测试证明拒绝生效**（读工作区外的文件、执行危险命令 → 都要被拒，并给出真实拒绝输出）。
6. **端到端证明**：从"另一端"发一条指令——"在共享工作区写一个文件并执行它"，本机真的写了、真的跑了、真的把 stdout 回传。

**判定标准**：第 4 步跑通（远程叫得动 + 真实输出回传）+ 第 5 步越权被拒（证明限制是真限制），才算"这台电脑变成了能被 AI 使用的服务器"。
只写完代码不跑通不算；按引擎规矩，须由另一个智能体独立复核通过才算验收。
